# アーキテクチャ決定記録 (decision.md / ADR)

本ドキュメントでは、`triage-agent` の設計および実装において行われた主要な技術的意思決定、背景、およびトレードオフを記録します。

---

## ADR-001: 開発言語およびコアSDKの選定
- **決定:** Python 3.11+（初期は3.9+、ADR-015にてEOL対応およびパフォーマンス向上のため3.11+へ引き上げ）、Google公式 `google-genai` SDK、および `pydantic` v2 を採用する。
- **背景:**
  - Geminiの最新機能（Function Calling, Google Search Grounding, Structured Outputs）を最も手軽かつ型安全に扱える。
  - セキュリティツール（Syft, Trivy, OSV）やデータ解析エコシステムとの親和性が高い。
- **トレードオフ:**
  - TypeScript環境への組み込みにはCLIサブプロセス呼び出しが必要だが、本システムはCI/CDや定期バッチでのCLI実行が主たるユースケースであるため問題ないと判断。

---

## ADR-002: SBOM入力フォーマットに Syft CycloneDX JSON を第一標準とする
- **決定:** Syftの出力形式（`syft scan ... -o cyclonedx-json`）および Syft native JSON を標準入力としてサポートする。
- **背景:**
  - 業界標準であり、推移的依存のPackage URL（PURL）やエコシステム情報（PyPI, npm, Maven等）を高い精度で保持している。
- **代替案との比較:**
  - 言語ごとのロックファイル（`package-lock.json`, `poetry.lock`）を個別にパースする方式はメンテコストが跳ね上がるため、Syftを一次前処理層と位置付けることで対応フォーマットを最大化した。

---

## ADR-003: 外部有償検索API（Tavily, SerpAPI等）を採用せず、Gemini標準検索とOSV APIで完結する
- **決定:** 
  1. 既知脆弱性の全件走査: **OSV.dev API (`/v1/querybatch`)**（完全無料・認証不要）
  2. コード・Advisory・コミット探索: **GitHub REST API**
  3. 事前予告（Pre-announcement）・ニュース探索: **Gemini Google Search Grounding**
- **背景:**
  - 運用のための追加APIキー契約や課金管理の負担を極小化するため。
  - OSV.devはGoogleが主導するオープンソース脆弱性DBであり、バッチ処理で数千件を数秒で返却可能。

---

## ADR-004: 指示書フォーマットの標準化（結論・CVSS・Yes/No確認ポイント・具体的確認方法）
- **決定:** 
  - 単なるCVSS値や一般的解説ではなく、「結論（期限とYes/No条件）」「CVE (CVSS)」「確認ポイント（Yes/No）」「具体的確認方法（ファイル名・XMLタグ・grepコマンド等）」「回避策」「未確認事項」「出典」を固定フォーマットとする。
- **背景:**
  - 従来の脆弱性スキャナの出力は「CVSS 7.5 High」と書かれていても「結局うちのシステムに影響があるのか？何をすればいいのか？」が分からないという現場のペインがあった。
  - 「下のポイントに1つでもYesなら○日以内に更新、全てNoなら次回定例リリースでOK」という意思決定基準を明示することで、初動速度を最大化する。

---

## ADR-005: 自社コードベース自動検証（補助CLI: verifier）の分離
- **決定:** 
  - トリアージ指示書の生成パイプラインとは疎結合な「補助CLI（`triage-verifier`）」として設計・実装する（ワンライナー実行も可能）。
- **背景:**
  - **外注委託システム:** 自社にソースがないため、生成された指示書（`triage_report.md`）をそのままベンダーに送付する。
  - **内製システム:** 自社でソースを持っているため、指示書の確認ポイントをツールで自動grep/走査し、Yes/Noを即座に判定する。
  - この両方のユースケースを無理なく満たすため、指示書JSONを仲介とした疎結合設計とした。

## ADR-006: モデル名の完全外出し設計
- **決定:**
  - コード内に `gemini-2.5-flash` などのモデル名をハードコードせず、`.env` の `GEMINI_MODEL` および役割別環境変数（`GEMINI_MODEL_PLANNER` 等）から動的に解決する。
- **背景:**
  - Geminiモデルは進化が極めて早く、コード改修なしに最新・最適モデルに切り替えられるようにするため。

---

## ADR-007: エンタープライズデータガバナンスとSBOM送信の安全管理方針 (Vertex AI対応)
- **決定:**
  - 社内・商用運用環境においては、個人向け無料枠ではなく **Google Cloud Vertex AI**（または商用有償契約のGemini API）経由での実行を標準方針とする。
- **背景:**
  - SBOM（自社システムの利用ライブラリ・バージョン一覧）はシステムの攻撃対象領域を示す機密情報である。
  - Google AI Studioの無料枠ではサービス改善のためにデータが利用される場合があるのに対し、Google Cloud Vertex AI では「顧客データ（入力プロンプトおよび生成データ）はGoogleの基盤モデル学習に利用されない（Customer Data is not used for model training）」ことが基本規約に明記されている（※キャッシュや不正利用検出・ログ保持等のポリシーはGoogle Cloudの最新の個別サービス利用条件に準拠）。
- **実装上の対応:**
  - `src/triage_agent/config.py` 内に `get_genai_client()` ファクトリを実装。環境変数 `GOOGLE_GENAI_USE_VERTEXAI=true`（または `VERTEX_AI=true`）と `GOOGLE_CLOUD_PROJECT`, `GOOGLE_CLOUD_REGION` を設定することで、コード改修なしにVertex AI経由の接続にシームレスに切り替わる構成とした。

## ADR-008: 手動監査サインオフの厳格突合と「安全」判定の防衛的設計
- **決定:**
  - `triage-verifier` における人手監査サインオフ（`AuditAttestation`）の照合において、部分一致やCVE単位での全項目一括承認を禁止し、`check_point_id` による完全一致を主キーとする。
  - `check_point_id` はインデックス番号（cp1等）ではなく、質問文とCVEの正規化ハッシュから決定論的に生成する（順序非依存）。
  - 各お知らせに含まれる確認ポイント構成から暗号指紋（`notice_hash`）を算出し、第2版で項目が追加・変更された場合は手動の版番号変更なしに過去のサインオフを自動失効させる。
  - サインオフの `status` が `NO` で始まっている場合のみ安全数（safe_count）として集約し、`YES` やその他が記録されている場合は要対応に倒す。
- **背景:**
  - 文字列の部分一致を行うと、`CVE-2026-11149` へのサインオフが `CVE-2026-111497` に誤爆するリスクが存在した。
  - 1つのCVEに対して複数の確認ポイントがある場合、あるいは版改訂で確認ポイントの並び順が入れ替わった場合、`cp1` のようなインデックス依存のIDでは誤った項目にサインオフが適用されてしまう。
  - 手動の `report_version` バンプに依存すると、版番号を上げ忘れた際に第2版の新規追加項目に古いサインオフが適用されて見落とす危険があった。
- **実装上の対応:**
  - `schemas.py` に `compute_check_point_id` および `compute_notice_hash` を実装。
  - ライブ推論結果・ドライラン双方でツール側がIDと指紋ハッシュを強制付与・検証。

## ADR-009: 「分からないことを作らない」原則とデモモードの完全分離
- **決定:**
  - ネットワーク障害時やシグナル0件時に、ドライランであってもそれらしい架空のCVE（Hallucinated CVEs）を生成する処理を禁止し、素直に「調査不能（0件）」として警告一覧に集約する。
  - デモ・展示・初回ウォークスルー用データは、明示的な `--demo` フラグと `DEMO-*` プレフィックスの付いた合成データに完全分離する。
- **背景:**
  - セキュリティシステムにおいて、実在しない架空のCVEや、過去のAdvisory URLと架空のCVE番号が組み合わさった「もっともらしい偽データ」が出力されることは、利用者に致命的な誤認を与えるリスクがある。
  - 「分からないことは分からないと正直に報告する（調査不能として警告）」ことがセキュリティトリアージの第一原則である。

## ADR-010: 正本（Official Baseline）管理モデルと製品名の正規化
- **決定:**
  - `check_point_id` 生成時の製品名プレフィックスには、LLMが付与した装飾文字列ではなく、正規化されたSBOMコンポーネント名（`normalize_component_name`）を採用する。
  - 運用上、AIエージェントの出力を直接照合するのではなく、人間が確認・確定した指示書JSONを「その版の正本（Official Baseline）」としてGit管理し、再検証やサインオフ照合は常に正本に対して実行するワークフローを標準とする。
- **背景:**
  - LLMは同一製品でも `brotli` や `Brotli (Node2Shell)`、`Brotli (HTTP2Shell)` など表現のブレが生じうる。
  - 実行ごとに質問文やIDが微細にブレると、以前作成したサインオフが当たらなくなり現場の疲弊を招く。
  - 「AIは版の下書きを作り、人間が承認した版を正本として固定する」ことで、IDの完全な安定性と安全な差分更新を実現する。

## ADR-011: Web GUI におけるCSRF/XSS防護・任意ファイル上書き遮断・Zero-CDN閉域網設計
- **決定:**
  - `web_ui.py` のローカルHTTPサーバーにおいて、外部悪意サイトからのクロスオリジン攻撃および任意ファイル上書きを4重の防護で遮断する：
    1. **Content-Type強制:** `application/json` 以外（ブラウザがCORS事前確認なしに送信できる `text/plain` 等）をHTTP 415で即時拒絶。
    2. **Host / Origin ヘッダー検証:** リクエスト元が `127.0.0.1:{port}` または `localhost:{port}` でない場合はHTTP 403で遮断。
    3. **動的CSRFトークン:** サーバー起動時に暗号学的に安全なランダムトークン（`secrets.token_hex(24)`）を生成し、全POSTリクエストで検証。
    4. **パストラバーサル遮断 (`resolve_safe_path`):** SBOM・自社コード・監査ファイルへの読み書きを作業ディレクトリ直下・配下に厳格制限（`../../` や絶対パスによるシステムファイル上書きを拒否）。
  - **XSSの根絶:** HTML属性内のインラインスクリプト呼び出し（`onclick="openSignoffModal('...')"`）を完全廃止し、`data-*` 属性とイベントデリゲーションによるDOM API取得に移行。
  - **Zero-CDN閉域網対応:** 外部CDN（Tailwind CDNやFont Awesome CDN）への依存を排除し、完全自己完結CSSおよび標準シンボルを採用。金融機関等の閉域ネットワークでも画面崩れや情報漏洩なく稼働可能とした。
- **背景:**
  - ローカルWeb GUIであっても、ユーザーが悪意のある外部Webページを開いた際にブラウザ経由で偽の「安全」サインオフが送信されたり、任意のローカルファイルが上書きされるリスクを完全に排除するため。

## ADR-012: コアパイプラインの単一情報源化（pipeline.py）と外注ベンダー回答記録の第一級市民化
- **決定:**
  - CLIとWeb GUIの実行処理を共通モジュール `src/triage_agent/pipeline.py` の `execute_triage_pipeline` に一本化し、コードの二重管理と挙動の乖離を解消。
  - 自社コードを持たない「外注・ベンダー委託システム」であっても、GUI上で早見表の確認ポイントごとにベンダー回答（例:「ベンダー確認済み・非該当」）やエビデンスを直接記録・保存できるよう `verify_codebase` を拡張。
- **背景:**
  - CLIで修正された仕様（上限省略コンポーネントの警告記録やドライラン時のフォールバック処理）がGUIに反映されないドリフトを防ぐため。
  - トリアージ指示書の最大の利用対象である「ソースコードのない外注システム運用部門」が、ベンダーへのヒアリング結果を正式な監査記録として残せるようにするため。

## ADR-013: トリアージ成果物の「攻撃地図化」リスクに対する機密性管理とデータ最小化方針
- **決定:**
  - `triage-agent` が生成する成果物（`triage_report.json`、`verification_audit_report.md`、`audit_signoff.json`）を、社内の最高機密情報（Confidential / Restricted）として位置づけ、以下の防御原則を設計・運用ルールとして確立する：
    1. **Gitリポジトリへの誤コミット防止:** `.gitignore` において実運用のレポート・サインオフ・SBOMファイルを網羅的に除外し、コミットを防止（デモ用の `sample_*.json` のみ許可）。
    2. **露出範囲の最小化（PRコメント・全社配信の抑制）:** CI/CD連携時、PRコメントやパブリックなビルドログには具体的な脆弱ファイル名・コード行番号・発火マップを平文で投稿せず、合否サマリのみを通知する。指示書・レポートの配布もシステム単位でスコープを分割し、全社一斉同報を避ける。
    3. **データの最小化と保持期限（TTLパージ）:** 脆弱性への対処（修正・回避策・パッチ）が完了した後は、詳細なコード検出箇所（行番号・スニペット）をパージし、「誰がいつどのような根拠で対応したか」という監査証跡の最小メタデータのみを長期保管する。
    4. **48時間ルールによる「地図の賞味期限短縮」:** 攻撃地図の漏洩リスクに対する最も本質的な防御は「穴が存在する期間（Exposure Window）を極小化すること」であると位置づけ、48時間以内の初動完了を徹底する。
- **背景:**
  - `triage-agent` の出力は、「どのシステムの、どのファイルの何行目に、どのような発火条件の未対応脆弱性があるか」という、攻撃者にとって最も価値の高い「高精度な攻撃の地図」そのものである。
  - 守る側にとって具体的で有用な情報であるほど、漏洩時のインパクトが甚大になるセキュリティツールの本質的ジレンマを踏まえ、ツールの仕様策定および組織運用の初期段階から機密性保護とデータ最小化を組み込む必要があるため。

## ADR-014: GitHub Token の必須化撤廃と OSV.dev API (OSV-Scannerバックエンド) への脆弱性調査一本化（Tokenless Architecture）
- **決定:**
  - `GITHUB_TOKEN` の必須扱いを撤廃し（任意補足扱いへ変更）、既知脆弱性スキャン・アドバイザリ調査の主軸を完全無料・認証不要の **OSV.dev API（OSV-Scannerのバックエンドデータベース）** に一本化する。
  - パッチコミット差分（Diff）の取得は、GitHub API の認証エンドポイントに依存せず、OSV レコード内の `references` から特定した公開 `.diff`（認証不要）または Gemini の Google Search Grounding による直接精読で行う。
  - GitHub REST API は、トークンが設定されている場合のみリリースタグ等の補助シグナル取得としてオプション利用し、未認証レート制限（403）に遭遇しても OSV で調査完了していれば致命的エラーとしない。
  - OSV.dev は言語パッケージ（PyPI, npm, Maven等）を主たる対象とするため、ランタイム本体やOS共有ライブラリなどOSV照会対象外となり得るものは「調査不能・要確認」として明示し、LLMが安易に安全側に引っ張られない安全側境界を確立する。
- **背景:**
  - 従来の実装では、GitHub REST API の未認証レート制限（60回/時）を緩和するために `GITHUB_TOKEN`（Personal Access Token）の利用を促す設計となっていた。
  - しかし、Personal Access Token や CI/CD シークレットの保持は、万が一のトークン漏洩時に組織のプライベートリポジトリへの不正アクセスや権限昇格を招く重大なセキュリティリスクを孕んでいる。
  - 特に金融機関やエンタープライズの閉域環境では、外部SaaS（GitHub）の認証トークンを発行・配備・ローテーションすること自体がセキュリティ審査の大きな障壁となっていた。
- **代替技術（OSV.dev API）の優位性:**
  - **完全トークンレス（Tokenless）:** APIキーや個人トークンが一切不要。レート制限も極めて緩く、バッチ照会（1回で数百パッケージ）が無償・無制限で実行可能。
  - **データの完全網羅性:** GitHub Security Advisories (GHSA) の全データがリアルタイムで OSV にミラーリングされているほか、NVD、PyPI、npm、Go、Rust、Maven、Linuxディストリビューション等の全エコシステムを網羅している。
  - **シークレット管理の極小化:** ツールが扱うクレデンシャルを「LLM推論用（Gemini API Key または GCP Vertex AI 認証）」のみに絞り込むことで、攻撃対象領域とシークレット管理コストをゼロにする。

## ADR-015: 稼働ランタイム環境の Python 3.11+ への引き上げ
- **決定:**
  - `requires-python` を `>=3.9` から **`>=3.11`** に引き上げ、公式サポート対象を Python 3.11+（推奨: Python 3.12+）とする。
- **背景:**
  - Python 3.9 は 2025年10月に公式サポート（セキュリティ修正を含む EOL）が終了しており、主要ライブラリ（`google-auth` 等）で EOL 警告（FutureWarning）が発生する状態となっていた。
  - セキュリティ製品である `triage-agent` 自体が EOL のランタイムに依存し続けることは、組織のセキュリティガバナンス上不適切である。
- **メリット:**
  - **パフォーマンス向上:** Python 3.11 で導入された Faster CPython（Specializing Adaptive Interpreter）により、大規模 SBOM の JSON パースや AST 構文木解析の処理速度が大幅に向上する。
  - **将来的な保守性:** `google-genai` SDK や `pydantic` v2 の最新機能との完全な互換性を確保し、将来の脆弱性パッチ適用を保証する。
  - **最新の型ヒント:** `str | None` や組み込みジェネリクス `list[str]` 等のモダンな型記述を完全標準化。

---

## ADR-016: Web GUI におけるゼロ依存 Server-Sent Events (SSE) リアルタイム進捗ストリーミングの導入
- **決定:**
  - Web GUI（DAWN Studio）において、外部ライブラリ（WebSocketライブラリや重いフレームワーク等）を一切追加せず、Python標準ライブラリの `http.server` による **Server-Sent Events (`/api/run-stream`)** を導入する。
  - フロントエンドに DAWN デザインシステムに準拠したプログレスバー、Phase インジケーター（1. Recon Planner → 2. Researcher → 3. Triage Agent）、パーセンテージ表示、およびリアルタイム調査対象コンポーネント表示を実装する。
- **背景:**
  - 複数コンポーネントを深層調査・LLM推論・パッチ差分精読する際、処理完了まで数十秒〜数分の待機時間が発生する。
  - 従来のUIではスピナーが回転するのみで現在の進行状況（どのフェーズか、どのライブラリを精読中か）が不可視であったため、ユーザーにフリーズと誤認される懸念や待ち時間ストレスが生じていた。
- **メリット:**
  - **ゼロ依存性の維持:** 外部の WebSocket サーバーや非同期フレームワーク（FastAPI/uvicorn等）を導入することなく、標準の `http.server` とブラウザ標準の `ReadableStream` だけで完結。
  - **UX の飛躍的向上:** リアルタイムで調査進行度（0〜100%）と現在調査中のパッケージ名が可視化され、待ち時間のストレスが解消される。
  - **下位互換性:** 既存の同期的 `/api/run` エンドポイントも維持され、自動テストやスクリプト連携への影響はゼロ。

## ADR-018: 「3つの鮮度」の運用原則と Self-Triage（自己診断ドッグフーディング）の導入
- **決定:**
  - 脆弱性トリアージが実効性を持つための前提条件として、以下の **「3つの鮮度（Three Dimensions of Currency）」** をシステムの運用設計原則として確立する：
    1. **対象システムの鮮度:** 塩漬けシステムに特効薬はない。普段からRenovate等で依存関係を最新に保つ運用があって初めて、トリアージ指示書による「48時間以内の初動完了」が可能となる。本ツールの導入自体が、組織内の塩漬け負債を可視化し、定期更新体制を確立するためのエビデンスとして機能する。
    2. **SBOM の鮮度:** 古いSBOMは誤警報と見落としの温床となる。CI/CDのリリース・ビルドパイプラインに組み込み、常に最新のビルド成果物から生成されたSBOMを診断対象とすることを義務付ける。
    3. **ツール自体の鮮度 (Self-Triage):** プロンプト、確認ポイントの型、外部API（OSV/GitHub）の仕様、LLMモデルは時間とともに風化する。`triage-agent` 自体も保守され続けるソフトウェアであると位置づけ、**「triage-agent 自身の SBOM を triage-agent 自体で定期的に自己診断する（Self-Triage CI / `--self-triage`）」** ドッグフーディング機構を標準実装する。
  - **CI/CD ガードレールと自動更新エコシステム:**
    - **非ゼロ終了コード制御 (`--fail-on unscanned,yes`):** 調査不能コンポーネント（API障害/上限到達）やYES判定（脆弱性該当コード検出）の発生時に非ゼロコードで停止し、CI上での「サイレントな成功」を完全に遮断。
    - **ロックファイル (`requirements-lock.txt`) と Dependabot:** 毎回最新版が入って自己診断が形骸化するのを防ぐため、固定バージョンロックファイルをコミットし、`.github/dependabot.yml` により pip 依存関係（`requirements-lock.txt`）および SHA 固定 GitHub Actions を週次で自動更新。
    - **ランタイム自身の補足と OSV 安全フィルタリング:** SBOM に Python ランタイム自身（`pkg:generic/python@...`）を漏れなく含めつつ、OSV API の仕様に準拠して `generic` purl はバッチ照会から安全にスキップし、Web/LLM 精読に回すことで外部 API の 400 エラーを防止。
- **背景:**
  - 「AIを導入すれば脆弱性対応が魔法のように解決する」という誤解を排し、「鮮度を保つ運用とセットで初めて効く実践的な道具」であることを組織的に担保するため。
  - 自分たちのツールの依存ライブラリ（`httpx`, `pydantic`, `google-genai` 等）を自分たちのツールで日常的に診断し続けることで、外部API仕様変更（OSVのレスポンス形式等）やモデルの陳腐化をツール開発者自身が誰よりも早く検知・自己修復できるようにするため。

## ADR-019: 実地試行（PoC）即応に向けた Verifier 実践的拡張とベンダー往復トラッキング（v0.3.0仕様策定）
- **決定:**
  1. **設定ファイル検証エンジンと主要3言語（JS/TS, Java, PHP）への Verifier 拡張:**
     - 発火条件の主要な分岐点となる設定ファイル（Tomcat `server.xml`、PHP `php.ini`、Nginx/Apache設定、JSON/YAML等）に対するキーバリュー・属性・ディレクティブ検証機構を新設する。
     - コード検証対象として、委託先および社内システムの主流である JavaScript/TypeScript、Java、PHP を追加し、コメント除外とテストコード自動分離を適用する（tree-sitter等の軽量解析活用）。
  2. **到達可能性（Reachability / Taint）解析への深入り見送り:**
     - 複雑なコールグラフ・到達解析による安易な「安全判定」は行わず、既存の「該当あり（YES）」「コード内未検出（外部設定要確認）」「手動確認/ベンダー照会要」の客観的3状態を維持し、「分からないものを安全と言わない」の原則を死守する。
  3. **ベンダー・委託先との往復ワークフロー支援（Excel / CSV 帳票エクスポート ＆ 回答インポート）:**
     - 生成されたトリアージ指示書（早見表）から、サイバーセキュリティ部・情シス・委託先との標準プロトコルである **Excel（.xlsx）および CSV（.csv）帳票** をワンクリック生成・出力可能にする。
     - ベンダーから返送された回答（Yes/No、確認者、確認日、根拠）を一括インポートし、タイムスタンプ付きの監査サインオフ（`audit_signoff.json`）として自動確定記録する。
  4. **客観的評価のための正解付きミニ評価セット（Benchmark Suite）の整備:**
     - 直近の実事例（auth0/node-jsonwebtoken, Tomcat/AJP, PHP/session, HTTP2Shell 等）を最小限の再現コード＆設定ファイルとして `benchmark/` に固定配置し、Verifier拡張時の見逃し（False Negative）および誤検知（False Positive）を機械的・定量的に測定可能にする。
- **背景:**
  - 実地試行（PoC）において直接測定・評価したいと考えられるKPIは、**「公開から配布までの時間短縮」** と **「ベンダー・現場との往復回数削減」** である。
  - 単に机上で対応言語を増やすよりも、直近の事例（TomcatのAJP/JNDIRealm設定やHTTP/2ディレクティブなど）で実際にトリアージ判断を分けた「設定ファイル」を直接検証できるようにすることが最も実効性が高い。
  - また、現場の連絡手段は依然として Excel/スプレッドシートが主流であり、相手のコミュニケーション形式に合わせたインポート/エクスポートおよび回答往復ログのタイムスタンプ記録が備わって初めて、「配布時間を◯時間から◯分に短縮、往復回数を◯回削減」という定量実績を提示できる。

## ADR-020: コミュニティ主導の事前予告カタログ（advisory_sources.toml）と iCalendar（.ics）連携による「緊急対応の計画作業化」
- **決定:**
  1. **コア・アイデンティティのピボット（「パッチの日を、前もって予定に入れられる」）:**
     - 本ツールの最重要の差別化軸・中核価値を「単なる既知CVEの事後スキャン」ではなく、**「SBOMからCVEが出る前の事前予告を拾い、パッチの日をカレンダーの予定に変える（突発的緊急対応を計画作業に変える）」** こととして再定義する。
  2. **事前予告（Pre-announcements）の2段階巡回アーキテクチャの確立:**
     - **1段目（決定論的定点巡回）:** オープンな宣言型カタログ `advisory_sources.toml` に基づき、各OSSプロジェクトの公式一次情報源（公式ブログ、announce ML、固定日程カレンダー）を決まった手順で直接取得。毎回同一の結果が得られ、APIキーも不要、かつ「巡回成功/失敗」を明示。
     - **2段目（LLM影響精読）:** 検出された予告テキストを Gemini で要約し、自社利用バージョンへの影響度および発火予測を構造化抽出。
     - **補助網（Web検索）:** カタログ未登録のマイナーOSSに限り、Google Search Grounding をフォールバック網としてオプション適用。
  3. **「コードではなくデータが堀になる」コミュニティ主導カタログ:**
     - 対象パッケージ名、公式URL/RSS/ML、予告パターン、公式度フラグ（`is_official: true/false`）を `advisory_sources.toml` に定義。
     - 一社では網羅できない世界中のOSS予告ソースを、利用者がPR（プルリクエスト）で持ち寄って拡充できるオープンデータ資産とし、利用者が増えるほどカタログが厚くなるネットワーク効果（堀）を築く。
  4. **偽情報・噂シグナルの防衛的分類（「調べなかったものを隠さない」原則の継承）:**
     - カタログ登録済みの公式一次ソースからの予告（「確定予告」）と、Web検索や非公式SNS等から拾われた未確認情報（「未確認の予兆」）をレポートおよび画面上で厳格に区別して表示する。
  5. **現場への出口としての iCalendar（`.ics`）標準連携:**
     - 自社SBOMに該当するコンポーネントの事前リリース予定日時（Node.js, OpenSSL, Oracle CPU, Patch Tuesday等）を、標準 iCalendar 形式（`.ics`）としてエクスポート可能にする。
     - Google カレンダーや Microsoft Outlook に直接インポートできるようにすることで、以下の実務的アクションを可能にする：
       - **人の手配:** リリース当日の輪番要員を厚くし、翌日に代休を事前設定。
       - **ベンダー確保:** 「◯曜日にリリース予定のため、翌朝に作業枠を確保」と事前仮押さえ。
       - **変更管理（RFC）の先回り起票:** 金融機関・大企業で日数を要する本番変更申請を事前起票し、パッチ公開後の「承認待ち待機ロス」を撲滅。
       - **心理的疲弊の軽減:** 突発的な深夜呼び出しをなくし、計画的な心づもりを確立。
- **背景:**
  - Tanium、Nexus IQ、Trivy、Snyk などの商用・OSS製品は強力だが、いずれも「CVE発行後の既知脆弱性の照合」が主戦場であり、事前予告の収集は手薄である。
  - セキュリティ現場・SRE・運用チームが最も疲弊している根本原因は「脆弱性の存在」そのものではなく、「金曜夕方などに突発的に降ってくる緊急対応（人の手配・ベンダー調整・変更申請パニック）」にある。
  - 事前予告の収集処理自体はスクレイピング技術としては平易だが、「どのプロジェクトが、どこで、どんな形で予告を出すか」の一覧データこそが真の価値であり、OSSのコミュニティモデルと極めて相性が良い。
  - 出口を Slack や Webhook のような設定前提ツールではなく、誰もが持つ標準カレンダー（ICS）にすることで、摩擦ゼロで現場の日常運用に溶け込ませることができる。

## ADR-021: 攻撃連鎖評価の運用手順化と、ディストリ中立なカーネル脆弱性の自動照会（v0.5.x）
- **決定:**
  0. **ディストリ中立の原則:**
     - 本ツールは OSS であり、特定のクラウド、ディストリ、オーケストレータを前提にしない。連鎖評価、層分類、昇格ルール、カバレッジ判定といった中核のロジックは、正規化した入力だけを扱い、特定ディストリの名前や特定クラウドの API を書かない。
     - 照会元（脆弱性データの取得先）と収集経路（テレメトリの配布と回収）は、共通の契約を持つ差し替え可能なアダプタとする。照会元が無い環境でも、手動台帳による評価、カバレッジ判定、影響範囲の表示はそのまま動き、自動照会できなかった事実は明示して要確認に倒す。
     - ディストリごとの対応状況（照会元、系統の区別、livepatch の扱い、既知の制約）を対応表として公開し、アダプタは ADR-020 の `advisory_sources.toml` と同じく宣言的な登録表で PR による寄稿を受ける。
  1. **3層分類（層 2 の上限は HIGH_UNVERIFIED）:**
     - 実機のカーネル版から自動で引いた脆弱性を、層 1「確証あり」（手動台帳、CISA KEV、出典付き PoC）、層 2「LPE の疑い」（CVSS の LPE 型、ディストリ重大度が高位、EPSS 閾値超え、メモリ破壊系 CWE）、層 3「その他の未修正」に分ける。修正版が未提供のものは別枠で目立たせる。
     - 層 2 は足場のあるプールでも `HIGH_UNVERIFIED`（2 週間）を上限とし、層の中は注視度で並べる。プールごとに「この版まで上げれば層 1・2 が全部解消する」版を示す。
  2. **前回実行との差分による決定論的な昇格:**
     - 実行ごとに CVE ごとの KEV、EPSS、CVSS ベクトル、ディストリ重大度、PoC 登録をスナップショットとして保存し、KEV 新規掲載、EPSS 急上昇、CVSS の LPE 型への改訂、出典付き PoC 登録のいずれかで層 2 を層 1 に昇格させる。`--fail-on promoted` で CI を止められるようにし、人による昇格は `--promote` で手動台帳に書き込む。
     - この仕組みは定期実行（毎日）を前提とする。
     - **実装時の補足（段階④）:**
       - 人による昇格は、手動台帳（`exploit_chain_ledger.json`）ではなく、専用の昇格台帳（`<--kernel-auto-state>/promotions.json`、出典 URL 必須）に書く。手動台帳に載せた CVE は自動照会の結果から外れるため、プールごとの露出判定と修正版が失われ、新しく増えたプールでの露出も見えなくなるためである。出典付き PoC の登録は、この `--promote` で扱う。
       - 昇格は露出が続く限り維持する（翌日の差分がゼロでも層 1 のまま）。露出がなくなれば外れる。手動昇格は台帳にある間だけ有効とする。
       - CVSS の「改訂」は、既存の採点からの引き上げに限る。初回の採点は昇格の理由にしない。照会元を切り替えた場合の値の違いも改訂とは扱わない。
       - CVSS の照会元は Red Hat Security Data API（`cve.json?package=kernel` の一括取得）とし、`kernel_sources.toml` の `[signals.cvss]` で差し替えられるようにする。2026-11-02 の事前検証（Amazon Linux 2023 の勧告にあるカーネル CVE から 400 件を抽出）では、CVSS v3 の網羅率が Red Hat 94%、NVD（kernel.org CNA の CVE）73%、取得時間が Red Hat 14 秒、NVD 31 分（API キーなし）だった。両方が採点した CVE でベクトルが一致したのは約 3 分の 1 のため、レポートには採点元を明記する。一括取得なので、利用者の環境についての情報（CVE 番号を含む）は送らない。
       - LPE 型（AV:L・PR:L/N・UI:N・高影響）で 7.0 以上という条件は、採点済みのカーネル CVE のうち Red Hat で 14%、NVD で 33% が満たす。1 プールあたり数百件になりうるため、これだけでは層 2 の条件にせず、層の中の並び順と昇格（引き上げの検知）に使う。
       - `--fail-on promoted` は「前回から新たに層 1 になったもの」があるときに発火する変化の通知とし、状態として止め続ける役は `critical_chain` が担う。オフライン実行（`--dry-run`）ではスナップショットを更新しない。
  3. **照会元アダプタ:**
     - 既定は対応範囲が最も広い OSV とする。OSV に ecosystem が無い Amazon Linux 向けに ALAS アダプタ（リポジトリメタデータ `updateinfo.xml` を中央で取得・解析、`latest` に対して判定）を用意する。RHEL は OSV の `Red Hat` ecosystem で足りるかを検証して決める。
     - **実装時の補足（段階⑤）:** RHEL は OSV の `Red Hat:enterprise_linux:<major>::baseos`（本流）を照会し、Red Hat Security Data API の CVE ごとの状態から「修正版がまだない CVE」（Affected・Fix deferred・Will not fix・New）を加える。勧告だけを見る照会元では、修正版のない CVE が見えないためである。ecosystem を `Red Hat` だけにすると EUS / AUS の系列の勧告が混ざり、本流の利用者の判定を誤るため使わない。EUS の利用者は本流と比べることになり、延長サポートで直った CVE も露出と出る（安全側）。系列の指定は今後の課題とする。また OSV は知らないパッケージにも空で答えるため、1 件も返らない場合はパッケージの記録の有無を確かめ、なければ照会不全とする（全ディストリ共通）。
     - すべてのアダプタは、系統が一致しない修正版を返さないこと、照会不全を件数で返すこと、出典 URL と取得日時を付けること（`provenance: auto`）を契約とし、同じ CVE が手動台帳にあれば手動を優先する。
     - livepatch は「適用中の livepatch がどの CVE を解消するか」という共通の形だけを中核で扱い、対応付けを返せないアダプタでは livepatch の存在だけで解消扱いにしない。
  4. **複数マシンからの収集を手順と仕組みの両方で支える:**
     - 収集スクリプトは標準出力に JSON を出すだけにとどめ、配布と回収は利用者の基盤に任せる。手順書は ssh を最初の例とし、kubectl やクラウドのリモート実行（AWS SSM など）は例の一つとして並べる。
     - 収集を実行した側が `collection_manifest.json`（対象、成功、失敗、届かなかったノード）を出す。期待ノード数に満たないプールでは「修正済み（SAFE）」「緩和済み」を出さず、`--telemetry-max-age` を超えたテレメトリは根拠に数えない。テレメトリと環境定義のプール ID の不一致は両方向とも警告する。
     - ノード ID は `/etc/machine-id` と組織ソルトから作る安定した匿名ハッシュとし、ホスト名を出さずに重複と欠落を数えられるようにする。
  5. **付随修正:** `nodes_count` と `collected_at` の未使用、`-p` 省略時の偽プールへの集約、無効化モジュール検出の `esp4/esp6/rxrpc` 固定、livepatch のフィールド不一致、コンポーネント名の外部照会への混入、環境定義の `kernel_package` の読み違いを直す。
- **背景:**
  - v0.4.0（ADR-019）の連鎖評価は、カーネル脆弱性をすべて手動台帳に頼っており、「台帳に載っていない致命的な LPE が残っていないか」という横展開の問いに答えられなかった。
  - 手順書は 1 台での実行例のみで、複数台からどう集めて突き合わせるのかが伝わっていなかった。コード側でも何台中何台集めたかを見ておらず、1 台分のテレメトリでプール全体が「実機確認済み」になっていた。安全側を重んじる設計の中で、ここだけ過信の方向に倒れていた。
  - 単一の照会元ですべてのディストリを網羅できない（OSV に Amazon Linux の ecosystem は無い）。照会元を決め打ちすると、それが無い環境の利用者にとって自動化が丸ごと使えなくなる。
- **トレードオフ:**
  - 層 2 を CRITICAL に上げないため、公表直後の危険な LPE が最初の実行では 2 週間扱いになりうる。代わりに昇格ルールと定期実行で、シグナルが変わった次の実行で必ず拾う。自動取得したカーネル CVE は CVSS 未採点や重大度の後日変更が多く、一律に CRITICAL にすると 48 時間対応の誤報が常態化して本物が埋もれるため、こちらを選ぶ。
  - 収集カバレッジを厳格に見るため、期待ノード数を書いていない、または一部のノードしか集めていない利用者には「要確認」が増える。未収集のノードに古いカーネルが残る見落としの方が重いため、受け入れる。
- **段階的な進め方:** ① カバレッジ・鮮度・プール不一致の検出と付随修正 → ② 手順書の書き直しと収集マニフェストの補助スクリプト → ③ 照会元アダプタの契約、OSV と ALAS、3 層分類 → ④ 昇格ルール → ⑤ RHEL → ⑥ 対応表と寄稿の手引き → ⑦ ベンチマークへの追加。進捗は `todo.md` の「柱 E」で管理する。

## ADR-022: 主な対象を「システム発注側の非専門家」に据え直し、検出の拡張より判断と証跡を優先する（v0.6.0）
- **決定:**
  1. **主な対象:**
     - 主な対象は、システム発注側の非専門家（IT 部門のシステム担当・ITPM）とする。セキュリティ担当は、その判断をレビューし、協働する側とする。
     - 機能の優先順位は、「ベンダーへの照会と回答の往復が、速く、確かになるか」で決める。
  2. **検出と資産管理は競わない:**
     - SBOM の継続監視は Dependency-Track に、コンテナや Kubernetes の設定の検出は Trivy や Kubescape などに任せ、triage-agent はその結果を取り込む側に立つ。
     - コンテナ境界の走査（todo 柱 B）は、自前の規則エンジンとしては作らない。検討の内容は保留として残す（[container-boundary-draft.md](container-boundary-draft.md)）。カーネル脆弱性のダイジェスト（柱 F）も保留とする。
  3. **攻撃連鎖とカーネルの自動照会（ADR-019 / ADR-021）は保守にとどめる:**
     - 0.5.x では、実機での通し確認で見つかる修正と、出し方の見直しだけを行い、新しいディストリや入力形式には広げない。
     - 出し方は、判定を突きつけるより、「インフラ担当やベンダーに確かめてもらう問い」として示す方向に寄せる。
     - `CRITICAL_CHAIN` は、構成の条件が揃ったことを示すもので、攻撃が成立することを確かめたものではない。このことをレポートで明示する。
  4. **v0.6.0 は往復の短縮に戻す:**
     - 柱 A（System Profile）
     - 判定と証跡の OpenVEX での書き出し
     - 実際の脆弱性対応 3〜5 件での試行と計測（柱 C・D の軽い版）
     - ⑤ のうち、既定の出力先の集約と保管期限
  5. **品質の示し方:** 評価セットの全件合格は、既知の型を壊していないことの確認にすぎない。試行で得た実例を評価セットに加え、判定できる範囲とできない範囲を明示することを重視する。
- **背景:**
  - v0.4.0〜v0.5.0 で攻撃連鎖とカーネルの機能が厚くなり、主に役立つ相手がインフラ担当やセキュリティ担当に寄り始めていた。v0.6.0 の当初案（コンテナ境界の走査、カーネルのダイジェスト）も、その延長だった。
  - 一方で、当初の重点を担う柱 A・C・D は後回しになっていた。当初の重点とは、「ベンダーの回答を待つ間に、非専門家がさっと確かめられる」ことである。
  - 外部の意見（2026-11-03）でも、次の 2 点が指摘された。検出と資産管理には成熟した OSS が多いこと。技術情報を、確かめられる問いと根拠付きの判断に変える部分に独自性があること。
- **トレードオフ:**
  - Kubernetes の利用者にとって、「LPE なしでノードに届く経路」（privileged など）は、当面ツールの判定に入らない。Trivy や Kubescape の結果を取り込む形で、必要になった時点で再検討する。
  - 攻撃連鎖とカーネルの機能は残るが、利用者からの要望があっても、0.6.0 では対象を広げない。
