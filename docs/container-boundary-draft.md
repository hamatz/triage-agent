# 保留中の検討: コンテナ境界の走査と攻撃連鎖への結合

> **この検討は保留しています（2026-11-03、[ADR-022](decision.md)）。** 主な対象を「システム発注側の非専門家」に据え直し、検出や設定の走査は既存のツール（Trivy、Kubescape など）に任せる方針にしたためです。
> 再開する場合も、ここにある規則の登録表や読み取り部品を自前で作るのではなく、既存のツールの結果を取り込む形から考えます。「LPE なしでノードに届く経路がある」「緩和策が迂回される」という問題の整理は、そのときの出発点として残しておきます。

## 問題

v0.4.0 以降の連鎖評価は、次の 2 つが揃うと Critical（48 時間）にしています。

- 足場: 外部から届く RCE、または信頼できないコードの実行
- 同じカーネルの未解消 LPE

この前提には、2 つの見落としがあります。

1. **LPE が要らない場合がある**: `privileged: true`、`CAP_SYS_ADMIN`、コンテナランタイムのソケットのマウントなどが付いたコンテナでは、足場さえあれば、カーネルの脆弱性がなくてもノードの root に届きます。カーネルを最新にしても、この経路は閉じません。いまの評価では、カーネルが修正済みなら `SAFE` と出てしまいます。CI の Docker-in-Docker（privileged）は、この典型です。
2. **緩和策が効かない場合がある**: modprobe で特定のモジュールを無効にする緩和策（例: Fragnesia の `install esp4 /bin/false`）は、`CAP_SYS_MODULE` や privileged を持つコンテナからは迂回できます。それでも「緩和済み（30 日）」と出てしまいます。

一方で、境界の設定を厳しくしても、カーネルの LPE は通常のシステムコール経由で届きます。restricted な Pod でも LPE の連鎖は成立するので、「厳しい設定だから期限を緩める」ことはしません（todo 柱 B「安易な緩和の禁止」）。

## 決定（案）

### 0. 原則

- **危険を上げる方向だけに使う**: 境界の走査結果で、既存の判定を下げることはしません。下げるのは、人が理由と期限を付けて分類したとき（決定 4）だけです。
- **オーケストレータ中立**: 入力の形式（Kubernetes のマニフェスト、Kubernetes の稼働中の Pod、Docker Compose、`docker inspect`）ごとに読み取り部品を分け、正規化した「コンテナの境界の事実」だけを中核が扱います。ADR-021 の照会元アダプタと同じ考え方です。
- **規則は出典付きの登録表に置く**: どの設定を何とみなすかは、コードではなく `chain/container_boundary.toml` に、出典と理由を付けて書きます。Kubernetes の Pod Security Standards（Baseline / Restricted）と、公開されている脱出手法を根拠にします。

### 1. 設定を 2 種類に分ける

| 種類 | 意味 | 例 | 連鎖評価への影響 |
| :--- | :--- | :--- | :--- |
| **境界の欠如** | 足場があれば、カーネルの脆弱性なしでノードの root に届く | `privileged: true`、`CAP_SYS_ADMIN`、`CAP_SYS_MODULE`、`CAP_DAC_READ_SEARCH`、`CAP_SYS_RAWIO`、`hostPID` と `CAP_SYS_PTRACE` の組、ホストの危険なパス（`/`、`/etc`、`/root`、`/proc`、`/sys`、`/dev`、`/var/lib/kubelet`、`docker.sock`・`containerd.sock` など）の hostPath マウント | 新しい連鎖として評価します（決定 2） |
| **攻撃面の拡大** | 単独ではノードに届かないが、LPE を使いやすくする、またはノードの外側に届く | `CAP_NET_ADMIN`、`CAP_NET_RAW`、seccomp `Unconfined`、AppArmor `unconfined`、`allowPrivilegeEscalation: true`、root での実行、`hostNetwork`（kubelet・クラウドのメタデータに届く）、`hostIPC`、`hostPID` 単独、`procMount: Unmasked` | 判定の段階は変えません。レポートに事実として示し、特定の緩和策を無効にします（決定 3） |

「攻撃面の拡大」で判定を上げない理由: いまの評価は、すでに「足場から LPE に届く」前提で Critical を出しています。これ以上は上げようがありません。また、seccomp `Unconfined` や `CAP_NET_RAW` は既定のままの Pod の多くに付いています。これで段階を上げると、ほぼすべてが同じ扱いになり、区別の役に立ちません。

### 2. 「境界の欠如」の連鎖

| ワークロードの露出 | 境界の欠如がある場合 |
| :--- | :--- |
| `internet_facing`（足場あり）、`untrusted_code`、`unknown` | `CRITICAL_CHAIN`（48 時間）。カーネルが修正済みでも出します。対処は設定の除去、または専用ノードへの隔離です。カーネルの更新では解消しないことを明記します |
| `internet_facing`（足場を自動判定できない） | `HIGH_UNVERIFIED`（2 週間） |
| `internal_only` | `HIGH_ISOLATED`（2 週間・横展開の起点） |

- 影響範囲（blast radius）は、カーネルの LPE と同じく、同じノードプールに同居するワークロードです。`hostNetwork` やノードの IAM ロールに届く場合は、その旨も書き添えます。
- レポートでは、カーネル CVE の連鎖とは別の行（例: `BOUNDARY:privileged`）として出し、どの規則に当たったか、出典、証跡の種類（決定 5）を示します。

### 3. 「攻撃面の拡大」と緩和策

- `kernel_mitigations.toml` の各緩和策に、その緩和を無効にする設定（例: モジュールの無効化 → `privileged`、`CAP_SYS_MODULE`）を書けるようにします。
- 該当する設定を持つワークロードについては、その緩和策を「未緩和」として扱います（`MITIGATED_NEEDS_PATCH` を出さない）。ノードの緩和策そのものは、他のワークロードには有効なままです。

### 4. 環境定義との対応付けと、人による分類

- 稼働中の Pod やマニフェストは、環境定義のワークロードに対応付けます。案としては、ワークロードに `match: {namespace, kind, name}`（またはラベルセレクタ）を書けるようにし、書いていなければ `namespace` と `id` で照合します。
- **どのワークロードにも対応しない「境界の欠如」のあるコンテナ**（CNI、CSI ドライバ、監視エージェントなどの DaemonSet に多い）は、露出度を `unknown` として扱います。これは既存の規約どおりで、安全側に倒して足場ありとみなすので、`CRITICAL_CHAIN` になります。
- そのままでは必要な特権を持つシステム部品で埋まってしまうため、**人による分類の台帳**（`boundary_classification.yaml` 仮）を用意します。名前空間とワークロードを指定し、次の項目を付けて露出度（多くは `internal_only`）を宣言します。
  - 理由
  - 確認者
  - 確認日
  - 期限
  - 期限が切れたら `unknown` に戻します。サインオフ（ADR-019 の TTL 付き）と同じ考え方で、境界の走査そのものは判定を下げず、下げるのは人の分類です。

### 5. 証跡の区別と収集

- **構成コード**（マニフェスト、`helm template` の出力、Compose）と**稼働中の実体**（`kubectl get pods -o json`、`docker inspect`）を区別して表示します。
- 両方ある場合は稼働中の実体を優先します。ミューテーティング Webhook などで実体が変わっている場合は、食い違いを警告します。
- 構成コードしかない場合は、「構成コード上は検出なし」とは書きますが、「境界は保たれている」とは書きません。
- **データの最小化**（ADR-013）: Pod の JSON には、環境変数（平文の秘密情報を含みうる）、引数、イメージの詳細などが含まれます。そこで収集補助スクリプト（`scripts/collect/collect_k8s_boundary.sh` 仮）では、`kubectl` の出力から境界の判定に要る項目だけを抜き出して保存します。項目は次のとおりで、原本は残しません。
  - 名前空間
  - 所有者の種類と名前
  - ノード名からプールへの対応
  - securityContext
  - host 系のフラグ
  - hostPath のパス
  - ケーパビリティ
  - seccomp / AppArmor
- ノードからプールへの対応には、ノードのラベル（例: `eks.amazonaws.com/nodegroup`）を使います。`collect_via_kubectl.sh` の `-l` と同じ考え方です。

### 6. レポートと CI

- 連鎖評価のレポートに「コンテナ境界」の節を足します。ワークロードごとに、境界の欠如、攻撃面の拡大、無効になった緩和策、証跡の種類、規則の出典を示します。
- `CRITICAL_CHAIN` の一部として、`--fail-on critical_chain` の対象になります。

## 段階的な進め方（案）

1. 規則の登録表、Kubernetes のマニフェストと稼働中の Pod の読み取り、決定 2 の連鎖、テスト
2. 環境定義との対応付け、人による分類の台帳、収集補助スクリプト（データ最小化）
3. 緩和策の無効化（決定 3）
4. Docker Compose と `docker inspect`（ECS / EC2 上の Docker、決めたいこと 2 しだい）
5. ベンチマークへの追加、手順書、対応表

## トレードオフ

- 特権を必要とするシステム部品は、分類の台帳に書くまで `CRITICAL_CHAIN` として出ます。最初の導入時に一度、棚卸しの手間がかかります。特権コンテナの見落としの方が重いため、受け入れます。
- 「攻撃面の拡大」では判定を上げないため、seccomp `Unconfined` などは事実の列挙にとどまります。段階を上げると区別がつかなくなるためです。

## 決めたいこと

1. **CI ランナー**: Docker-in-Docker などで privileged の CI ランナーを使っていますか？　使っている場合、`untrusted_code` × privileged は、毎日 `CRITICAL_CHAIN` として出続けます。実態としては正しい評価です。ただ、対処（rootless のビルド、kaniko、専用ノードへの隔離など）が済むまで、`--fail-on critical_chain` が CI を止め続けます。この扱いでよいか、それとも「専用ノードに隔離済み」を人が宣言できる余地を設けるか。
2. **Kubernetes 以外**: ECS（EC2 起動タイプ）や、EC2 上で直接 Docker を動かしているものはありますか？　どちらを Kubernetes の次に対応するかを決めたいです。
3. **人による分類の台帳**: 決定 4 の考え方（走査は下げない、下げるのは期限付きの人の分類）でよいか。既存のサインオフ（`audit_signoff.json`）に載せるか、別の台帳にするか。
4. **Helm**: ツールの中で Helm を展開せず、`helm template` の出力を読む前提でよいか。
