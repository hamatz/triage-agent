# ADR-021（下書き）: 攻撃連鎖評価の運用手順化と、ディストリ中立なカーネル脆弱性の自動照会

- **状態:** 提案（レビュー待ち）
- **対象版:** v0.5.x（ADR-019 / v0.4.0 の連鎖評価エンジンを拡張）
- **設計原則:** 本ツールは OSS であり、特定のクラウド、ディストリ、オーケストレータを前提にしない。特定環境向けの部品は、共通の契約に従う差し替え可能なアダプタとして提供する。実装の順序は需要に応じて決めてよいが、中核のデータモデルと判定ロジックに特定環境の前提を入れない。

---

## 決定

### 0. ディストリ中立の原則

- **中核は環境に依存しない。** 連鎖評価、層分類、昇格ルール、カバレッジ判定は、正規化した入力（下記の「プール実機情報」と「カーネル脆弱性エントリ」）だけを扱う。特定ディストリの名前や、特定クラウドの API を中核のコードに書かない。
- **照会元と収集経路はアダプタにする。** どちらも共通の入出力契約を持つ。新しいディストリやクラウドへの対応は、アダプタを 1 つ足すだけで済むようにする。
- **未対応の環境でもツールは役に立つ。** 照会元のアダプタが無いディストリでも、手動台帳による連鎖評価（v0.4.0 の機能）、カバレッジと鮮度の判定、ブラストラディウスの表示はそのまま動く。自動照会できなかった事実は「照会元なし」として明示し、安全側（要確認）に倒す。黙って `SAFE` にしない。
- **どの環境でも同じ安全基準を守る。** 系統（フレーバー）の不一致で修正済みと判定しない、出典の無いデータで判定しない、照会の失敗を件数で開示する、といった既存の原則は、すべてのアダプタが満たすべき契約とする。
- **対応状況を公開する。** ディストリごとの対応状況（照会元、系統の区別方法、livepatch の扱い、既知の制約）を対応表として docs に載せる。利用者が自分の環境で何が自動化され、何が手動のままかを事前に分かるようにする。

### 1. 層ごとに扱いを分け、層 2 は HIGH_UNVERIFIED を上限とする

実機のカーネル版から自動で引いた脆弱性は、件数が膨大になるため 3 層に分けて扱う。

| 層 | 条件 | 連鎖評価での扱い |
|---|---|---|
| 1. 確証あり | 手動台帳に登録済み、CISA KEV 掲載、出典付き PoC あり | 現行どおり（足場ありなら `CRITICAL_CHAIN`） |
| 2. LPE の疑い | CVSS が `AV:L` かつ `PR:L` かつ `C:H/I:H`、ディストリ重大度が高位、EPSS が閾値超え、メモリ破壊系 CWE のいずれか | 連鎖評価にかけるが上限は `HIGH_UNVERIFIED`（2 週間）。「自動推定」と明記 |
| 3. その他の未修正 | 上記に当たらない | 件数のみ表示 |
| 別枠 | ディストリに修正版が未提供 | 「パッチ待ち・緩和策のみ」として目立たせる |

- 判定に使うシグナルのうち、KEV、EPSS、CVSS、CWE は CVE 単位でディストリに依存しない。ディストリ重大度だけはディストリごとに尺度が違う（例: Important / Moderate、high / medium）ため、各アダプタが共通の 4 段階（critical / high / medium / low）に写像して返す。写像の表は対応表に載せる。
- 層 2 の中は「注視度」（当てはまるシグナル数、EPSS、ディストリ重大度）で並べ、足場のあるプールの項目を上に出す。期限は変えない。
- プールごとに「この版まで上げれば層 1 と層 2 が全部解消する」版（該当 CVE の修正版の最大値）を出す。版の比較は既存の `version_parser`（dpkg / rpm 規則）を使い、比較規則が分からないディストリでは表示しない。

### 2. 層の昇格を前回実行との差分で決定論的に行う

Fragnesia（CVE-2026-46300）の教訓は、公表時の分類の誤りではなく、状況が変わった後に評価し直さなかったことにある。そこで、静的な分類の精度よりも変化の検出を重視する。

- 実行ごとに評価対象のスナップショット（CVE ごとの KEV、EPSS、CVSS ベクトル、ディストリ重大度、PoC 登録の有無）を `triage-output/chain_state/` に保存する。
- 前回と比べて次のいずれかが起きたら、層 2 を層 1 に昇格させる。
  - KEV に新たに掲載された
  - EPSS が急上昇した（既存の `epss_history` と `--epss-threshold` を流用）
  - CVSS ベクトルが改訂され、LPE の型になった
  - 出典付きの PoC が登録された
- レポートの先頭に「前回から昇格したもの」の欄を置く。`--fail-on promoted` で CI を止められるようにする。
- 人が判断して昇格させる経路として `--promote CVE-xxxx --source-url …` を用意する。手動台帳に書き込む形にし、既存の出典方針（`source_url` と `retrieved_at` が必須）にそのまま乗せる。
- この仕組みは定期実行を前提とするため、手順書で「毎日実行」を標準とする。実行の仕組み（cron、CI のスケジュール、各種ジョブ基盤）は問わない。

### 3. 照会元アダプタ

**共通の契約:**

- 入力: プール実機情報（`os_distribution`、`os_release`、カーネルのパッケージ名と系統、パッケージ版、適用中の livepatch）。
- 出力: カーネル脆弱性エントリの一覧。各エントリは CVE、系統ごとの修正版（または「修正版なし」）、共通 4 段階に写像したディストリ重大度、出典 URL、取得日時、`provenance: auto` を持つ。
- 照会に失敗した、あるいは解析できなかった件は、黙って捨てずに「照会不全」として件数を返す。
- 系統が一致しない修正版を返さない（例: 汎用カーネルの修正版を、クラウド向けカーネルの修正版として返さない）。
- 同じ CVE が手動台帳にあれば、手動台帳を優先する（中核側で処理する）。
- アダプタは宣言的な登録表（ADR-020 の `advisory_sources.toml` と同じ考え方）で中核に登録し、利用者が PR で追加できるようにする。

**当初のアダプタ:**

| アダプタ | 対象（例） | 照会元 | 備考 |
|---|---|---|---|
| OSV（汎用） | Ubuntu、Debian、AlmaLinux、Rocky Linux、SUSE / openSUSE、Azure Linux など、OSV に ecosystem があるディストリ | OSV.dev | 対応範囲が最も広いため、既定のアダプタとする。既存の `extract_osv_fixed_ranges()` を一般化して使う |
| ALAS | Amazon Linux 2023 / 2 | ALAS（リポジトリメタデータ `updateinfo.xml`） | OSV の ecosystem に Amazon Linux は無いため、個別に用意する |
| Red Hat | RHEL | Red Hat の CSAF/VEX、または OSV の `Red Hat` ecosystem | OSV で足りれば個別アダプタは作らない。検証で決める |
| なし | 上記以外（Bottlerocket、Container-Optimized OS、独自ビルドのカーネルなど） | — | 「照会元なし」と明示し、手動台帳と要確認で運用する。対応表に載せ、アダプタの寄稿を募る |

**ALAS アダプタの方針:**

- 中央で `latest` リリースのリポジトリメタデータを取得してキャッシュし、カーネル系パッケージの勧告から「CVE → 修正版 NEVRA → 重大度」を抜き出す。ホスト側は今までどおり読み取り専用でパッケージ版を返すだけにする。
  - AWS は `updateinfo.xml` を自前で解析するより `dnf` API を使うよう推奨しており、自前で解析する場合は rpm-metadata の仕様に従うよう求めている。その仕様どおりに実装し、解析できなかった勧告は照会不全として件数を開示する。
- 出典は勧告ページの URL（例: `https://alas.aws.amazon.com/AL2023/ALAS-2024-581.html`）とメタデータの取得日時とする。
- 勧告 ID はウェブ上の形（`ALAS-2024-581`）と dnf 上の形（`ALAS2023-2024-581`）が異なる。ID は不透明な文字列として扱い、両方を保持する。
- 1 つの CVE が複数の勧告に現れること、勧告の CVE リストと重大度は後から変わりうることを前提に、差分検出（決定 2）の対象に含める。
- AL2023 はパッケージ名で系統が分かれる（例: `kernel` と `kernel6.12`）。AL2 は Extras のリポジトリごとに勧告が分かれる。系統が一致しない修正版で修正済みと判定しない。
- AL2023 のリリースのメタデータは公開後に更新されないため、特定のリリースに固定されたホストからは新しい勧告が見えない。判定は必ず `latest` に対して行い、推奨対応には「リリース固定を外す、または `--releasever` を指定して更新する」旨を出す。

**livepatch の扱い（全アダプタ共通）:**

- livepatch の仕組みはディストリごとに違う（Canonical Livepatch、kpatch、AL の `kernel-livepatch` パッケージなど）。中核では「適用中の livepatch が、どの CVE を解消するか」という共通の形だけを扱い、対応付けは各アダプタが返す。
- 対応付けを返せるアダプタでは、カーネルが修正版以上であるか、該当 livepatch が適用されていれば、その CVE を解消扱いとし、レポートでは「livepatch で解消（次回カーネル更新を推奨）」と区別する。返せないアダプタでは、livepatch の存在だけでは解消扱いにしない。

**ホスト側の補助確認（任意）:** ディストリのパッケージマネージャによる照合（例: `dnf updateinfo`）は、リポジトリへの通信とキャッシュ更新が起きて読み取り専用の約束から外れるため、既定では無効のオプションとする。

### 4. 複数マシンからの収集を、手順と仕組みの両方で支える

**手順書（docs/exploit-chain.md）を次の 6 段で書き直す。**

1. 棚卸し: `environments.yaml`（プール、ワークロード、露出度）
2. 収集: 各ノードで `collect_kernel_telemetry.sh`（読み取り専用、POSIX sh）
3. 回収と照合: プールごとに集め、何台中何台集まったか、鮮度を確認
4. 台帳同期: 手動台帳と自動照会（決定 3）
5. 評価: `--chain-audit`
6. 定期実行と CI: 毎日の実行、`--fail-on critical_chain` / `promoted`

**収集経路は特定の基盤に依存させない。** 収集スクリプトは標準出力に JSON を出すだけにとどめ、配布と回収は利用者の基盤に任せる。手順書には、どの基盤でも当てはまる最小の例（ssh で `sh -s < script`）を最初に示し、続けて代表的な経路の例を並べる。

- 汎用: ssh のループ、Ansible の `script` モジュール
- Kubernetes（マネージドかどうかを問わない）: `kubectl debug node/<name>` で `chroot /host` して実行
- クラウドのリモート実行: AWS SSM Run Command、Google Cloud の OS Config / VM Manager、Azure の Run Command など
- 物理サーバ、オンプレミスの仮想基盤: 汎用の経路を使う

プールの対応付けも、特定のタグやラベルの名前を前提にしない。収集時に `-p` で渡す値を、利用者がどこから取るか（クラウドのタグ、Kubernetes のノードプールのラベル、構成管理のグループ名など）を例として示すにとどめる。

**収集マニフェストとカバレッジ判定:**

- 収集を実行した側が、プールごとに `collection_manifest.json` を出す。中身は、対象にしたノード、成功、失敗、届かなかったもの、収集日時の一覧だけとし、形式を公開する。どの基盤からでも生成できる単純な JSON にする。
- 代表的な経路（ssh / Ansible、kubectl、AWS SSM）向けに、マニフェストを作る補助スクリプトを例として同梱する。それ以外の基盤では、利用者が同じ形式で出せばよい。
- 期待ノード数は、マニフェストがあればマニフェストから、無ければ環境定義の `nodes` / `nodes_count` から取る。どちらも無い場合は「期待ノード数不明」と明示する。
- 期待ノード数に満たないプールは「実機確認済み」を名乗らず、`SAFE` を出さない。
- `--telemetry-max-age`（既定 7 日）を超えたテレメトリは根拠に数えない。
- テレメトリにしか無いプールと、環境定義にしか無いプールを両方とも警告する。
- ノード ID は `sha256(ホスト固有の識別子 + 組織ソルト)` の先頭 12 桁とする。識別子は `/etc/machine-id` を既定とし、取れなければホスト名を使う。ホスト名やインスタンス ID を出さずに重複と欠落を数えられるようにする。

### 5. 付随して直す既存の不具合

- `nodes_count` を読んでいるが使っていない（決定 4 のカバレッジ判定で使う）。
- `collected_at` を使っていない（決定 4 の鮮度判定で使う）。
- `-p` を省略すると `pool_id` が `node_id` の既定値 `"anonymized-node"` に落ち、全ノードが 1 つの偽プールにまとまる。`-p` を必須にするか、プールの無いテレメトリを拒否して警告する。
- `load_node_telemetries` で、無効化モジュールの検出対象が `esp4/esp6/rxrpc` に固定されている。`kernel_mitigations.toml` の `required_modules` から組み立てる。
- 収集スクリプトは `livepatch_active`（真偽値）しか出さないが、ローダは `livepatch_modules` を読む。決定 3 の livepatch 判定のため、適用中の livepatch の識別子（パッケージ名と版、または livepatch モジュール名）を出すようにする。
- フレーバー判定のフォールバックが、特定のクラウド名（aws / gcp / azure / oracle）の文字列一致に頼っている。ソースパッケージ名（dpkg の `source:Package`、rpm の `SOURCERPM`）を正として扱い、文字列一致は取れなかった場合の補助にとどめる。Ubuntu の HWE は `linux-hwe` ではなく `linux-hwe-6.11` のような版番号付きの名前で照会する必要がある。
- `target_cves.extend(wl.components)` により、`php` などのコンポーネント名が KEV/EPSS/OSV への照会に混ざる。data-handling の方針（内製パッケージ名を外に出さない）に反するため、CVE/GHSA の形のものだけを送る。
- 環境定義の見本で `kernel_package` が、パッケージ名とパッケージ版の両方として読まれている。

## 背景

- v0.4.0 の連鎖評価は判定ロジックが丁寧な一方で、カーネル脆弱性はすべて手動台帳への登録が前提だった。登録された CVE しか見ないため、「台帳に載っていない致命的な LPE が残っていないか」という横展開の問いに答えられなかった。
- 手順書は 1 台での実行例のみで、複数台からどう集め、どこで突き合わせるのかが利用者に伝わっていなかった。コード側でも何台中何台集めたかを見ておらず、1 台分のテレメトリでもプール全体が「実機確認済み」になっていた。安全側を重んじる設計の中で、ここだけ過信の方向に倒れていた。
- 単一の照会元ですべてのディストリを網羅できない。OSV は対応範囲が広いが、Amazon Linux のように ecosystem が無いディストリもある。照会元を 1 つに決め打ちすると、それが無い環境の利用者にとって、自動化の部分が丸ごと使えなくなる。
- 提案者の環境（Amazon Linux と RHEL が中心）は、本ツールの利用者の一例にすぎない。OSS として、Ubuntu、Debian、その他のディストリ、オンプレミス、他のクラウドの利用者にも同じ価値を届ける必要がある。

## 層 2 を CRITICAL に上げない理由

- 自動で引いたカーネル CVE は、CVSS が未採点のもの、重大度が後から変わるものが多い。足場のあるプールで層 2 を全部 CRITICAL にすると、48 時間対応の誤報が常態化し、本物の CRITICAL が埋もれる。
- 跳ね上がる脆弱性は、昇格ルール（決定 2）で次の定期実行で必ず拾う。層 2 を上げすぎない代わりに、変化に追従する速さで安全側を担保する。

---

## 検証が必要な点（実装前に小さく確かめる）

1. OSV の版指定照会で、主要ディストリ（Ubuntu、Debian、Alma / Rocky）のカーネルパッケージをどこまで網羅できるか。系統（クラウド向けカーネル、HWE など）の区別が ecosystem とパッケージ名で成り立つか。
2. ALAS の `updateinfo.xml` から、カーネル系パッケージの「CVE → 修正版」を安定して抜き出せるか。AL2023 の `latest` と AL2 の Extras で、取得元と系統の区別が成り立つか。
3. RHEL の照会元として、OSV の `Red Hat` ecosystem で足りるか、Red Hat の CSAF/VEX が必要か。修正予定なしや調査中の状態がどう表現されるか。
4. 各ディストリの重大度を共通 4 段階へ写像する表の妥当性。
5. 各ディストリの livepatch と CVE の対応付けを、照会元から機械的に取れるか。

## 段階的な進め方

1. 付随修正と、カバレッジ・鮮度・プール不一致の検出（決定 4、5）。全環境に効き、小さく済む。
2. 手順書の書き直し、収集マニフェストの形式の公開、代表的な経路の補助スクリプト（決定 4）。
3. 照会元アダプタの共通の契約と登録の仕組み、3 層分類、プールごとの「この版まで上げれば解消」表示（決定 0、1、3）。最初のアダプタとして、対応範囲が最も広い OSV と、OSV で賄えない Amazon Linux 向けの ALAS を同時に作り、契約が 2 種類の照会元で成り立つことを確かめる。
4. スナップショットと昇格ルール、`--fail-on promoted`、`--promote`（決定 2）。
5. 検証 3 の結果に応じた RHEL の対応。
6. ディストリごとの対応表を docs に公開し、アダプタ寄稿の手引きを書く。
7. ベンチマークへの追加: 層 2 から層 1 への昇格、収集が欠けたプールで `SAFE` を出さないこと、系統違いで修正済みと誤判定しないこと、livepatch での解消、照会元が無いディストリで要確認に倒れること。ディストリごとのケースを用意し、アダプタを追加するときの回帰テストにも使う。
