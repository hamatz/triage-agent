# ADR-021（下書き）: 攻撃連鎖評価の運用手順化と、カーネル脆弱性の自動照会（ALAS 優先）

- **状態:** 提案（レビュー待ち）
- **対象版:** v0.5.x（ADR-019 / v0.4.0 の連鎖評価エンジンを拡張）
- **前提:** 主な稼働基盤は EC2（Amazon Linux が大半、次いで RHEL）。Kubernetes（主に EKS）は 2〜3 割。外部照会はオンラインで可。

---

## 決定

### 1. 層ごとに扱いを分け、層 2 は HIGH_UNVERIFIED を上限とする

実機のカーネル版から自動で引いた脆弱性は、件数が膨大になるため 3 層に分けて扱う。

| 層 | 条件 | 連鎖評価での扱い |
|---|---|---|
| 1. 確証あり | 手動台帳に登録済み、CISA KEV 掲載、出典付き PoC あり | 現行どおり（足場ありなら `CRITICAL_CHAIN`） |
| 2. LPE の疑い | CVSS が `AV:L` かつ `PR:L` かつ `C:H/I:H`、ディストリ重大度が Important 以上、EPSS が閾値超え、メモリ破壊系 CWE のいずれか | 連鎖評価にかけるが上限は `HIGH_UNVERIFIED`（2 週間）。「自動推定」と明記 |
| 3. その他の未修正 | 上記に当たらない | 件数のみ表示 |
| 別枠 | ディストリに修正版が未提供 | 「パッチ待ち・緩和策のみ」として目立たせる |

- 層 2 の中は「注視度」（当てはまるシグナル数、EPSS、ディストリ重大度）で並べ、足場のあるプールの項目を上に出す。期限は変えない。
- プールごとに「この版まで上げれば層 1 と層 2 が全部解消する」版（該当 CVE の修正版の最大値）を出す。カーネルはまとめて上げるものなので、CVE の一覧より行動に直結する。

### 2. 層の昇格を前回実行との差分で決定論的に行う

Fragnesia（CVE-2026-46300）の教訓は、公表時の分類の誤りではなく、状況が変わった後に評価し直さなかったことにある。そこで、静的な分類の精度よりも変化の検出を重視する。

- 実行ごとに評価対象のスナップショット（CVE ごとの KEV、EPSS、CVSS ベクトル、PoC 登録の有無）を `triage-output/chain_state/` に保存する。
- 前回と比べて次のいずれかが起きたら、層 2 を層 1 に昇格させる。
  - KEV に新たに掲載された
  - EPSS が急上昇した（既存の `epss_history` と `--epss-threshold` を流用）
  - CVSS ベクトルが改訂され、LPE の型になった
  - 出典付きの PoC が登録された
- レポートの先頭に「前回から昇格したもの」の欄を置く。`--fail-on promoted` で CI を止められるようにする。
- 人が判断して昇格させる経路として `--promote CVE-xxxx --source-url … ` を用意する。手動台帳に書き込む形にし、既存の出典方針（`source_url` と `retrieved_at` が必須）にそのまま乗せる。
- この仕組みは定期実行を前提とするため、手順書で「毎日実行」を標準とする。

### 3. 照会元をアダプタとして差し替えられるようにし、ALAS から作る

入力は各プールの実機情報（ディストリ、リリース、カーネルのパッケージ名、パッケージ版）とし、「このパッケージ版に影響する脆弱性」を引く。照会元はディストリごとのアダプタにする。

| 優先 | 対象 | 照会元 | 備考 |
|---|---|---|---|
| 1 | Amazon Linux 2023 / 2 | ALAS（`updateinfo.xml`） | OSV の ecosystem に Amazon Linux は無い |
| 2 | RHEL | Red Hat の CSAF/VEX、または OSV の `Red Hat` ecosystem | どちらを使うかは検証で決める |
| 3 | Ubuntu / Debian / Alma / Rocky | OSV | 既存の `extract_osv_fixed_ranges()` を活用 |
| — | 上記以外（Bottlerocket など） | なし | 「照会できなかった」と明示し、要確認に倒す |

**ALAS アダプタの方針:**

- 中央で `latest` リリースのリポジトリメタデータ（`updateinfo.xml`）を取得してキャッシュし、カーネル系パッケージの勧告から「CVE → 修正版 NEVRA → 重大度」を抜き出す。ホスト側は今までどおり読み取り専用でパッケージ版を返すだけにする。
  - AWS は `updateinfo.xml` を自前で解析するより `dnf` API を使うよう推奨しており、自前で解析する場合は rpm-metadata の仕様に従うよう求めている。その仕様どおりに実装し、解析できなかった勧告は「照会不全」として件数を開示する。
- 出典は勧告ページの URL（例: `https://alas.aws.amazon.com/AL2023/ALAS-2024-581.html`）とメタデータの取得日時とし、`provenance: auto` を付ける。同じ CVE が手動台帳にあれば手動を優先する。
- 勧告 ID はウェブ上の形（`ALAS-2024-581`）と dnf 上の形（`ALAS2023-2024-581`）が異なる。ID は不透明な文字列として扱い、両方を保持する。
- 1 つの CVE が複数の勧告に現れること、勧告の CVE リストと重大度は後から変わりうることを前提に、差分検出（決定 2）の対象に含める。
- **系統（フレーバー）の区別:** AL2023 はパッケージ名で系統が分かれる（例: `kernel` と `kernel6.12`）。AL2 は Extras のリポジトリごとに勧告が分かれる。既存の Ubuntu フレーバー分離と同じく、系統が一致しない修正版で「修正済み」と判定しない。
- **リリース固定の罠:** AL2023 のリリースのメタデータは公開後に更新されないため、特定のリリースに固定されたホストからは新しい勧告が見えない。判定は必ず `latest` に対して行い、推奨対応には「リリース固定を外す、または `--releasever` を指定して更新する」旨を出す。
- **livepatch:** livepatch の勧告は別リポジトリにあり、パッケージ名に対象カーネル版が入る。カーネルが修正版以上であるか、該当 livepatch が適用されていれば、その CVE は解消扱いとする（AWS の説明どおり）。レポートでは「livepatch で解消（次回カーネル更新を推奨）」と区別する。
- **ホスト側の補助確認（任意）:** `dnf updateinfo --releasever=latest --list` をホスト上で実行して、中央の判定と照合するモードを用意する。リポジトリへの通信とメタデータのキャッシュ更新が発生し、厳密な読み取り専用ではなくなるため、既定では無効にする。

### 4. 複数マシンからの収集を手順と仕組みの両方で支える

**手順書（docs/exploit-chain.md）を次の 6 段で書き直す。**

1. 棚卸し: `environments.yaml`（プール、ワークロード、露出度）
2. 収集: 各ノードで `collect_kernel_telemetry.sh`（読み取り専用）
3. 回収と照合: プールごとに集め、何台中何台集まったか、鮮度を確認
4. 台帳同期: 手動台帳と自動照会（決定 3）
5. 評価: `--chain-audit`
6. 定期実行と CI: 毎日の実行、`--fail-on critical_chain` / `promoted`

**収集経路:**

- **EC2（主経路）:** SSM Run Command（`AWS-RunShellScript`）でスクリプトを配り、結果は S3 に出力する。対象はタグ（例: `triage:pool`）か Auto Scaling Group で絞り、同じ値を `-p` に渡す。
- **EKS:** マネージドノードグループのノードは EC2 なので同じ SSM 経路で集める。プールはノードグループのラベルで対応付ける。
- **SSM の入っていないノード:** `kubectl debug node/<name>` で `chroot /host` して実行する手順を補助として載せる。

**収集マニフェストとカバレッジ判定:**

- 収集時に、プールごとに `collection_manifest.json`（対象にしたノード、成功、失敗、届かなかったもの、収集日時）を出す補助スクリプトを用意する。SSM の場合は、コマンドの呼び出し結果（対象インスタンスごとの成否）がそのまま期待ノードの集合になる。オートスケーリングでノードが入れ替わる環境でも、「対象にしたのに取れなかった」を正確に数えられる。
- 期待ノード数に満たないプールは「実機確認済み」を名乗らず、`SAFE` を出さない。
- `--telemetry-max-age`（既定 7 日）を超えたテレメトリは根拠に数えない。
- テレメトリにしか無いプールと、環境定義にしか無いプールを両方とも警告する。
- ノード ID は `sha256(インスタンス ID + 組織ソルト)` の先頭 12 桁とし、ホスト名や ID を出さずに重複と欠落を数えられるようにする。

### 5. 付随して直す既存の不具合

- `nodes_count` を読んでいるが使っていない（決定 4 のカバレッジ判定で使う）。
- `collected_at` を使っていない（決定 4 の鮮度判定で使う）。
- `-p` を省略すると `pool_id` が `node_id` の既定値 `"anonymized-node"` に落ち、全ノードが 1 つの偽プールにまとまる。`-p` を必須にするか、プールの無いテレメトリを拒否して警告する。
- `load_node_telemetries` で、無効化モジュールの検出対象が `esp4/esp6/rxrpc` に固定されている。`kernel_mitigations.toml` の `required_modules` から組み立てる。
- 収集スクリプトは `livepatch_active`（真偽値）しか出さないが、ローダは `livepatch_modules` を読む。決定 3 の livepatch 判定のため、適用中の livepatch パッケージ名と版を出すようにする。
- RPM 系のフレーバーを SRPM 名から取っているため、AL2023 の `kernel6.12` などが正しく区別されるか確認する。Ubuntu の HWE は `linux-hwe` ではなく `linux-hwe-6.11` のような版番号付きの名前で照会する必要がある。
- `target_cves.extend(wl.components)` により、`php` などのコンポーネント名が KEV/EPSS/OSV への照会に混ざる。data-handling の方針（内製パッケージ名を外に出さない）に反するため、CVE/GHSA の形のものだけを送る。
- 環境定義の見本で `kernel_package` が、パッケージ名とパッケージ版の両方として読まれている。

## 背景

- v0.4.0 の連鎖評価は判定ロジックが丁寧な一方で、カーネル脆弱性はすべて手動台帳への登録が前提だった。登録された CVE しか見ないため、「台帳に載っていない致命的な LPE が残っていないか」という横展開の問いに答えられなかった。
- 手順書は 1 台での実行例のみで、複数台からどう集め、どこで突き合わせるのかが利用者に伝わっていなかった。コード側でも何台中何台集めたかを見ておらず、1 台分のテレメトリでもプール全体が「実機確認済み」になっていた。安全側を重んじる設計の中で、ここだけ過信の方向に倒れていた。
- 利用環境の大半は Amazon Linux だが、OSV の ecosystem 定義に Amazon Linux は無い。OSV だけを照会元にすると、主な環境が丸ごと自動照会の対象外になる。

## 層 2 を CRITICAL に上げない理由

- 自動で引いたカーネル CVE は、CVSS が未採点のもの、重大度が後から変わるものが多い。足場のあるプールで層 2 を全部 CRITICAL にすると、48 時間対応の誤報が常態化し、本物の CRITICAL が埋もれる。
- 跳ね上がる脆弱性は、昇格ルール（決定 2）で次の定期実行で必ず拾う。層 2 を上げすぎない代わりに、変化に追従する速さで安全側を担保する。

## 検証が必要な点（実装前に小さく確かめる）

1. ALAS の `updateinfo.xml` から、カーネル系パッケージの「CVE → 修正版」を安定して抜き出せるか。AL2023 の `latest` と AL2 の Extras で、それぞれ取得元と系統の区別が成り立つか。
2. RHEL の照会元として、Red Hat の CSAF/VEX と OSV の `Red Hat` ecosystem のどちらがカーネルの修正版を網羅しているか。修正予定なしや調査中の状態がどう表現されるか。
3. Ubuntu のカーネルパッケージに対する OSV の版指定照会の網羅性（前回の作業環境からは OSV API に届かず未確認）。
4. AL2023 のホスト上の `dnf updateinfo` で CVE ID まで取れるか（補助確認モードの成立条件）。

## 段階的な進め方

1. 付随修正とカバレッジ・鮮度・プール不一致の検出（決定 4、5）。小さく、すぐ効く。
2. 手順書の書き直しと、SSM 収集と収集マニフェストの補助スクリプト（決定 4）。
3. 検証 1 と ALAS アダプタ、3 層分類、プールごとの「この版まで上げれば解消」表示（決定 1、3）。
4. スナップショットと昇格ルール、`--fail-on promoted`、`--promote`（決定 2）。
5. 検証 2 と RHEL アダプタ。
6. ベンチマークへの追加: 層 2 から層 1 への昇格、収集が欠けたプールで `SAFE` を出さないこと、系統違いで修正済みと誤判定しないこと、livepatch での解消。
